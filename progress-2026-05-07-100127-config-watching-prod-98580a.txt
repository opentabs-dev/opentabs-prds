## 2026-05-07 - US-008
- Added `MCP client receives tools/list_changed notification after config.json adds a plugin in production mode` test to `e2e/config-watcher-prod.e2e.ts`.
- Test opens a GET /mcp SSE stream using the established session ID to receive server-pushed notifications. Uses `ReadableStream.getReader()` to parse SSE data lines in real time and detects `notifications/tools/list_changed`.
- Also fixed a bug in `platform/mcp-server/src/file-watcher.ts`: `startConfigWatching` was not starting mtime polling when `fs.watch()` failed with EMFILE in production mode (because `fw.mtimePollTimerId === null` — mtime polling was never started in production mode without `startFileWatching`). This caused all prod-mode config watcher tests to fail when inotify instances were exhausted.
- Files changed: `e2e/config-watcher-prod.e2e.ts`, `platform/mcp-server/src/file-watcher.ts`
- **Learnings for future iterations:**
  - GET /mcp with `mcp-session-id` header opens an SSE stream for server-pushed notifications. Use `ReadableStream.getReader()` with a `TextDecoder` to parse `data:` lines in real time.
  - When `controller.abort()` is called after resolving, the `ReadableStream.read()` throws `AbortError` — catch and swallow it since it's expected.
  - `startConfigWatching` EMFILE fallback only called `startMtimePolling` when polling was already running (from `startFileWatching`). Production mode never calls `startFileWatching`, so the EMFILE fallback was a no-op. Fix: unconditionally call `startMtimePolling` after clearing any existing timer.
  - The EMFILE condition for `fs.watch()` is common when 128 inotify instances (Linux default) are exhausted during parallel E2E tests. The mtime polling fallback is the only detection mechanism in that case.

## Codebase Patterns
- Health endpoint `pluginDetails` now includes `urlPatterns: string[]` (effective patterns including those derived from url-type settings). Added in US-005.
- `settings-resolver.ts` handles url-type settings as `Record<string, string>` (instance name → URL), not plain strings. Each entry derives a `*://host/*` match pattern.
- `writeTestConfig` auto-generates `permissions` with `{ permission: 'auto' }` for each plugin by basename — no need to explicitly set permissions in most tests.

- `startConfigWatching` EMFILE fallback: must unconditionally call `startMtimePolling` regardless of whether polling was already running — in production mode it was never started, so the old guard `if (fw.mtimePollTimerId !== null)` was always false.
- reload.ts `reloadCore`: callbacks created by `createFileWatcherCallbacks` is now shared between unconditional config watching and the dev-only plugin file watchers.
- `stopFileWatching` at top of `reloadCore` stops ALL watchers (including config watcher) before re-creating them — intentional, must not be removed.
- dev-mode.ts simply exports `isDev()` as a plain boolean — the only file to edit for dev mode detection semantics.
